# V0.4 · 单实例锁

> **一句话目标**：同一时刻只允许一个实例运行——第二次启动时提示"已经在运行"，然后退出。

如果没有这道锁，真实场景会这样：开机自启拉起一个实例，用户又双击了一次图标，于是**同一段时间被两套采样记了两遍**，报表直接翻倍。这类错误很难发现，因为界面上看不出任何异常。

---

## 前置条件

V0.3 完成：日志可用，异常不再凭空消失。

## 要做什么

用 Windows 的**命名互斥体（named mutex）**做进程间互斥。

Windows 内核对象（mutex / event / semaphore）可以带名字，名字在整个系统（或当前会话）内唯一。第二个进程用同一个名字创建时，系统不会新建，而是返回**已存在的那个**，并通过 `GetLastError()` 告诉你 `ERROR_ALREADY_EXISTS`（183）。

这是 Windows 上做单实例的标准做法，比"扫进程列表"或"写 PID 文件"都可靠——进程被强杀时，内核对象会自动释放，不会留下僵尸锁。

---

## 关键 API

```python
import ctypes
kernel32 = ctypes.windll.kernel32

# 1) 创建（或打开）命名互斥体
handle = kernel32.CreateMutexW(None, False, r"Local\ManualInfoCollect")

# 2) 立刻读错误码，判断是不是"已经存在"
ERROR_ALREADY_EXISTS = 183
if kernel32.GetLastError() == ERROR_ALREADY_EXISTS:
    ...  # 已有实例在跑
```

要点：

| 项 | 说明 |
|---|---|
| 名称前缀 `Local\` | 当前登录会话内唯一；`Global\` 是整机（跨用户），一般不需要 |
| 名称 | 建议 `Local\<APP_NAME>`，避免和别的程序撞名 |
| 必须保存句柄 | 用全局变量接住，否则被 GC 回收 → 锁失效 |
| 不要 `CloseHandle` | 进程退出时系统自动释放；提前关等于主动放锁 |
| `GetLastError` 时机 | 必须在 `CreateMutexW` 之后、任何其他 API 调用之前读 |

## 实现步骤

1. 写 `acquire_single_instance() -> bool`
2. 全局变量 `_mutex_handle` 接住返回值，并在函数里 `global` 声明
3. 在 `--run` 入口、日志初始化之后、**采集启动之前**调用
4. 失败时：写一条 WARNING 日志 + `MessageBoxW` 提示"程序已在运行，看右下角托盘"
5. 返回 1（非 0），让脚本以错误码退出

> 为什么弹窗而不是静默退出：用户双击图标后什么都没发生，会以为程序坏了。托盘图标可能被折叠在 `^` 里，提示必须主动给。

## 坑

| 坑 | 表现 | 处理 |
|---|---|---|
| 句柄被 GC 回收 | 锁时灵时不灵 | 用模块级变量持有，注释写清"必须保住引用" |
| 忘记读 `GetLastError` | 永远认为自己是唯一实例 | 紧跟 `CreateMutexW` 读 |
| 用了 `Global\` 前缀 | 切换用户后互相干扰 | 个人程序统一用 `Local\` |
| 两个"不同名字" | 锁不生效 | 名字要用常量，不要在两处各写一遍 |
| 在 `--run` 之外也抢锁 | `status` / `install` 被误拦 | 只在常驻入口抢锁 |

## 验收标准

- [ ] 启动第一个实例，正常运行
- [ ] 再启动第二个，立即弹出提示并退出，退出码非 0
- [ ] 日志里能看到"已有实例在运行"的记录
- [ ] 任务管理器强杀第一个实例后，可以正常启动新实例（锁自动释放）
- [ ] `status` / `install` 不受锁影响
