个人信息采集与查看系统 · 技术方案

版本：V1.0（待确认） 日期：2026-11-12 对应 PRD：PRD_个人信息采集与查看系统.html（已定稿）

0. 设计前提（来自 PRD 决策）

  • 多台 Windows + 多台 Android 采集，单用户查看，5 分钟周期，任何数据保留 ≤30 天。
  • App 实时拉取、本地不缓存；Android 不做常驻通知，允许采集缺口。
  • 传输全程 HTTP（2026-11-12 更新）：服务端部署于自用阿里云 ECS，采集端与查看端直连公网地址，不上 HTTPS；二期小程序受平台规则约束时再另行启用。
  • 主数据库（2026-11-12 更新）：MySQL 8.0，复用服务器上已运行的 docker 容器；不引入 Redis。
  • 开发者熟悉 Python，其余栈视为可学习的新栈。

1. 技术选型

组件选型理由
Windows 采集端Python 3.11+ · psutil · pywin32 · pystray · PyInstallerpsutil 覆盖 CPU/内存/磁盘/网络/开机时长；pywin32 取前台窗口与显示器；PyInstaller 打包免安装 exe；全部在熟悉的 Python 栈内
GPU / 电池健康pynvml（NVIDIA）/ WMI 电池 · wmiPRD Q1 扩展字段；非 NVIDIA 机型 GPU 留空，符合"不支持字段留空"约定
公网 IP外部 API（如 api.ipify.org）+ 本地缓存 30 分钟避免每 5 分钟都打外部接口
服务端Python FastAPI + Uvicorn + MySQL 8.0 + APSchedulerMySQL 8.0 复用云服务器上已运行的 docker 容器（2026-11-12 确认，替代原 SQLite 方案），顺带练真实数据库；个人规模（≤10 台设备 × 每天 288 报告 ≈ 3 千行/天）毫无压力；APScheduler 做 30 天清理与小时/天聚合。Redis 不引入（设计中无必须用它的场景）
传输协议全程 HTTP：Uvicorn 监听 0.0.0.0:8100，两端直连云服务器（2026-11-12 确认，不做 HTTPS）个人自用项目接受明文传输，省掉证书与反代环节；代码层用 base_url 配置，将来要上 HTTPS 仅改配置
Android 端已确认uni-app（Vue3）一套代码做采集与查看 UI；uni API 覆盖电量/设备信息/网络状态，图表用 lime-echart；二期微信小程序同一代码库直接编译，与 PRD 二期规划天然衔接
Android 定时采集uts/原生插件封装 Android AlarmManager，每 5 分钟拉起短时采集任务WorkManager 最小周期 15 分钟不满足要求；uni-app 后台定时能力依赖原生插件，是 M3 的主要技术点；接受 Doze 模式下的缺口（PRD 已确认）
本地缓存（两端）断网补推队列，7 天上限Windows 端用 Python sqlite3；uni-app 端用 plus.sqlite 或 JSON 文件队列，容量小（最多 2016 条）
Android 端已确认使用 uni-app（Vue/JS）。学习成本为 Vue 基础语法；最大收益是二期微信小程序复用同一代码库。需要重点验证的技术点：App 后台 5 分钟定时采集依赖原生插件，M3 第一周先做可行性验证（spike），若插件生态不满足再评估自写 uts 模块。

本地不缓存业务数据
▼ HTTP（全程）· JSON · 设备令牌 / JWT
云服务器（阿里云 ECS）FastAPI（Uvicorn 直跑 HTTP:8100）
接收 API · 查询/导出 API · 绑定与登录

服务端为单体应用，不拆微服务：个人项目规模下，一个 FastAPI 进程 + 一个 MySQL 库（服务器现有容器）即可承载全部职责，部署 = ECS 上一个常驻进程（systemd/nohup）。

3. 数据协议

3.1 上报包（两端通用）

{
  "report_id": "uuid-v4",          // 幂等去重键
  "device_id": "dev_xxx",          // 绑定/登录后由服务器签发
  "collected_at": 1731379500,      // 采集时刻，epoch 秒（东八区仅用于展示）
  "metrics": {
    // Windows 专有
    "cpu": {"model": "...", "cores": 8, "percent": 32.1},
    "mem": {"total": 17179869184, "used": 10485760000},
    "disks": [{"name": "C:", "total": ..., "used": ...}],
    "gpu": {"vendor": "nvidia", "model": "...", "percent": 15},  // 不支持则 null
    "battery": {"health_percent": 87},   // 台式机/手机按实际
    "display": {"resolution": "2560x1440"},
    "net": {"sent_bytes": 123456, "recv_bytes": 654321},   // 周期增量
    "ips": {"local": ["192.168.1.10"], "public": "x.x.x.x", "mac": ["..."]},
    "uptime_seconds": 15120,
    "foreground": {"app": "chrome.exe", "title_head": "...", "active_seconds": 298},
    // Android 专有
    "battery": {"level_percent": 48, "charging": false, "temp_c": 31.5},
    "net_type": "wifi"
  }
}

规则：report_id 重复 → 服务器只留第一份；metrics 中不支持的字段传 null，不得伪造；foreground.active_seconds 之和 ≤ 周期长度。

3.2 API 一览

方法/路径用途鉴权
POST /v1/bindingsWindows 端申请绑定码（返回 6 位码 + 10 分钟有效）无（限流：每 IP 每分钟 1 次）
POST /v1/bindings/{code}/claimApp 输入绑定码，为设备签发 device_id + device_tokenJWT（主人）
POST /v1/auth/login主人账号登录，签发 JWT；Android 登录即自动注册本机为采集端账号密码
POST /v1/reports上报数据包（含补推，body 为数组支持批量）device_token
GET /v1/devices设备列表 + 在线状态 + 最近上报时间JWT
GET /v1/devices/{id}/latest最新一份完整指标（详情页）JWT
GET /v1/devices/{id}/history?metric=&range=24h|7d|30d趋势数据（24h 原始 / 7d 小时聚合 / 30d 天聚合）JWT
GET /v1/devices/{id}/export?metrics=&from=&to=&format=csv导出 ≤30 天数据，返回 CSV 文件流JWT
DELETE /v1/devices/{id}解绑设备（令牌立即失效，历史数据留至自然过期）JWT

3.3 存储结构（MySQL 8.0）

  • devices(id, name, type, token_hash, bound_at, unbound_at)
  • reports(id, device_id, collected_at, payload_json) —— 原始包整存，30 天删除
  • metrics_hourly / metrics_daily(device_id, bucket, key, value) —— 由 APScheduler 滚动聚合，同样 30 天删除；趋势查询走聚合表，不扫原始表
  • bindings(code, device_pending, expires_at)、app_settings

4. 安全设计

  • 传输全程 HTTP 明文（2026-11-12 用户确认接受，不做 HTTPS）；设备令牌 + 密码在公网明文传输，风险已知悉并接受。
  • 数据库连接参数走环境变量，密码不进代码、不进 git；业务不用 root 账号，另建最小权限账号。MySQL/Redis 端口不对公网暴露（现为 0.0.0.0，部署时收敛为仅本机访问）。
  • 设备令牌只存哈希；采集端令牌只有写权限，读接口一律 JWT。
  • 单用户密码存 argon2 哈希；登录与绑定接口限流。
  • 服务器时间校验：拒绝 collected_at 偏离接收时刻 ±24 小时的报告（PRD 假设值）。

5. 关键风险与对策

风险影响对策
Android 5 分钟精确闹钟在国产 ROM 上被省电策略压制数据缺口比预期多PRD 已接受缺口；App 内提供"自启动/电池优化白名单"引导页（仅引导，不强制）
前台窗口识别在 UAC 弹窗/全屏游戏下不准软件时长偏差取不到焦点时记为"系统空闲"，与 PRD 口径一致
公网 IP 外部 API 限流/不可用IP 字段缺失缓存 30 分钟 + 失败置 null，不阻塞整包上报
MySQL 容器/宿主机故障丢历史数据（可容忍，30 天滚动）每日 mysqldump 到同机备份目录，保留 7 份

6. MVP 迭代路径（每步都有可验证产物）

  1. M1 打通链路：FastAPI 服务端（接收+存储+latest 查询）+ Windows 采集端脚本版（无托盘，命令行跑）→ 用 curl 能查到电脑数据。验收：一台电脑连续 1 小时每 5 分钟一条报告入库。
  2. M2 采集端完善：绑定码流程、PyInstaller 打包、托盘常驻、断网补推、GPU/电池/显示器字段。验收：两台电脑完成绑定并同屏在线。
  3. M3 Android 采集：先做 uni-app 后台定时采集可行性验证（spike），再实现登录即采集上报（闹钟 5 分钟 + 本地队列）。验收：手机数据出现在服务器，缺口符合预期。
  4. M4 查看端：概览页 + 详情页 + 趋势图（24h/7d/30d）+ 导出 CSV。验收：完整走通 PRD 核心旅程。

M1/M2 全程 Python，可以在学 uni-app/Vue 之前就拿到第一个可运行系统——这是刻意的顺序：先验证你最熟的端，再引入新栈。

7. 决策记录

Android 端框架：uni-app（Vue3），2026-11-12 由需求方确认，不采用 Flutter/Kotlin。理由：查看端 UI 开发效率高 + 二期微信小程序复用同一代码库。
